# Prompts Used

> Act as a product-minded senior engineer. Turn the dealership-inventory brief into a traceability matrix that separates explicit assignment requirements, confirmed product decisions, and implementation conventions. Use TypeScript/Express, React/Tailwind, and persistent file-backed SQLite. Preserve customer-only registration, one local first-Admin bootstrap, Admin-only inventory mutations, one-vehicle stock decrement per purchase, hard delete, currency-specific minor-unit prices, and the explicit absence of payment processing and purchase-history records. Identify non-goals and propose focused acceptance tests.

> Design a typed REST API with shared request/response contracts, versioned SQLite migrations, and secure authentication. Public registration must create Customers only; provision the first Admin through a one-time local interactive CLI, with no default credentials or public role-promotion route. Hash passwords, validate inputs strictly, enforce roles at the API boundary, use generic login failures and rate limits, and keep secrets out of source control. Start with focused tests, run them to observe the expected failures, implement the smallest complete solution, then rerun the tests and type checks. Do not add production seed data or fake authentication.

> Build the inventory API and React screens for authenticated catalog/search, Admin create/full-update/restock/hard-delete, and Customer one-unit purchase requests. Keep UI affordances consistent with server-side authorization; zero-stock vehicles remain visible and cannot be purchased. Model loading, validation, success, failure, empty-catalog, and filtered-empty states explicitly. Make the purchase action an inventory decrement only; no checkout, charge, reservation, receipt, order, or history ledger. Add executable tests before each behavior change and do not ship placeholders, fake responses, or demo-data fallbacks.

> Implement currency-aware vehicle prices without floating-point persistence. Accept decimal strings at the API boundary, determine the supported ISO currency precision, convert exactly to integer minor units, and format values without losing precision. Require a currency for any price bound; never compare or convert prices across currencies. Validate reversed ranges and unsafe values, escape SQL wildcard characters in text search, and bound pagination. Write contract and repository tests for zero-decimal, two-decimal, and other supported precision cases before changing implementation.

> Review the stock mutation paths for races and stale Admin forms. Make a purchase a single conditional database update that decrements exactly one unit only when stock is positive; restock must be atomic and must reject quantity overflow. Add a vehicle revision, increment it on update/purchase/restock, return it in DTOs, and require the observed revision through `If-Match` for Admin update/delete. Test concurrent last-unit purchases, an Admin edit after a Customer purchase, stale delete, and a populated database migration before implementing. Verify failed operations leave the latest row unchanged.

> Review the React catalog and Admin workflows at narrow mobile widths and with keyboard-only interaction. Give every field a visible label, preserve clear focus indicators, announce meaningful status/errors, and keep the purchase and stock states truthful. Treat confirmation dialogs as real modal interactions: move focus inside, contain Tab navigation, support Escape when safe, and restore focus to a sensible target. Use automated accessibility checks as targeted evidence, but do not claim full WCAG conformance without a complete manual audit.

> Make first-run behavior reproducible and safe. A fresh local database should remain empty after migration; an operator should create the first Admin interactively without exposing the password in command arguments or shell history. Keep synthetic vehicles and accounts exclusively in isolated test fixtures, label screenshots as test data, and ensure normal startup never substitutes demo records. Surface failed logout or failed refresh operations instead of reporting success. Verify the behavior with isolated file-backed database and browser tests.

> Verify the repository as it exists, not as documentation suggests it behaves. Run formatting, lint, type checks, unit/integration tests, browser journeys, production build, dependency audit, and current-tree plus Git-history secret/data scans. Record the actual runtime versions, exact pass/fail counts, test limitations, and any corrected failure. Separate runtime-tested behavior from code inspection, inference, and untested claims.
